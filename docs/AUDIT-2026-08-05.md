# Scintilla Run hardening audit — 2026-08-05

## Scope

This audit reviewed the active `scintilla-run` repositories and pull requests
against the organization policy: semantic conflict resolution, explicit
architecture ownership, exact-head review, truthful CI evidence, fail-closed
security, bounded transports, durable state, and synchronized GitHub/Linear
records.

## Merged during this audit

### Operator authentication

`scintilla-app-rs` now fails closed when `SCINTILLA_ALLOWED_EMAIL` is absent or
invalid. The previous hard-coded fallback could silently grant access after a
deployment misconfiguration. The merged parser is private to the binary,
bounded to the email maximum, ASCII-only, control/whitespace-free, and rejects
malformed local/domain and header-smuggling forms.

- Pull request: `scintilla-run/scintilla-app-rs#5`
- Reviewed head: `1d3ddfc8fa5e059175ff269ba28aad91ca04577e`
- Merge: `d67336dd94b7166141565c584b6e5f03808ba7a3`

### Interfaces and release routing

`scintilla-interfaces` now preserves the already-merged function resource and
concurrency configuration contract while adding immutable revisions, weighted
aliases, sync/async invocation through revisions and aliases, invocation status,
and cancellation. Integrity tests require configuration and release routes to
coexist and reject obsolete `/versions` operation names.

The feature branch was behind current `main`, but the intervening commits only
added disjoint Zed package files. The merge therefore combined both intentions
rather than selecting one side's tree.

- Pull request: `scintilla-run/scintilla-interfaces#10`
- Reviewed head: `1235566102cdf4cb4b112faff7a1a906d7fd9c9c`
- Merge: `d4e75ffd33284679b3393b12504de2b415f1554b`

### MCP process boundary

`scintilla-mcp-server.rs` now separates operating-process bootstrap and stdio
lifecycle from the existing product-domain Lambda/BEAM runtime module. The
binary is a thin Tokio adapter; bootstrap owns telemetry startup, sanitized
startup fields, MCP service construction, root span, stdio transport, and
shutdown. Architecture tests ratchet stdout ownership and prevent domain/runtime
concerns from drifting back together.

- Pull request: `scintilla-run/scintilla-mcp-server.rs#13`
- Reviewed head: `c3fd209ce6fbdb0d4a961bfa54eb1c6d82f2caf4`
- Merge: `85f0afd6fb790459e26ab46529c32f7c4bbe000a`

## MCP consolidation decision

Four overlapping MCP bootstrap pull requests existed. They do not represent four
independent features.

- `#13` contained the clean process/domain structural separation and was merged.
- `#14` contains the narrow immutable shared-bootstrap dependency and resource
  attribute parser delegation. It is **not merge-ready**: `Cargo.toml` adds the
  git dependency, but the branch's `Cargo.lock` blob is identical to `main` and
  contains no shared-bootstrap package. A `cargo --locked` build would therefore
  fail. This branch must remain draft until the lock is genuinely regenerated
  and the post-#13 source is reconciled.
- `#10` is a stale earlier shared-bootstrap proposal with no meaningful current
  diff and should be closed as superseded.
- `#11` combines the structural extraction already merged from `#13` with useful
  collector endpoint validation and resource bounds. The structure is
  superseded; the endpoint hardening should be rebuilt as a focused follow-up on
  current `main`, then combined with the corrected `#14` dependency adoption if
  their final APIs align.

The next MCP pull request should contain only:

1. a real immutable shared-bootstrap dependency plus a regenerated lockfile;
2. delegation of identity and secret-safe resource parsing;
3. bounded credential-free HTTP(S) OTLP endpoint validation;
4. tests pinning the revision, resource limits, duplicate-key behavior,
   reserved identity keys, endpoint authority, and stdout purity;
5. no tool, prompt, resource, runtime-route, or execution-authority change.

## CI evidence boundary

Multiple Scintilla repositories currently receive GitHub Actions conclusions
before a runner starts. Jobs expose no steps and no logs. Those conclusions are
tracked as organization runner-admission evidence and are not represented as
passing tests or as code failures.

During the outage:

- no check may be removed, converted to `continue-on-error`, or bypassed merely
  to create a green conclusion;
- security-critical bounded changes may merge only after exact-head static
  review, no unresolved threads, and explicit recertification tracking;
- larger execution, persistence, migration, and release changes remain draft
  until their native suites can actually execute.
